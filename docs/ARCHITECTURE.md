# معماری تربت من

## معماری اجراشده

Monorepo با pnpm: `apps/api` شامل Fastify، Drizzle، PostgreSQL/PGlite و فضای فایل خصوصی؛ `apps/citizen-web` شامل React، React Router، TanStack Query، Vite و PWA؛ `apps/admin-web` ورودی مستقل کارتابل با رابط و قراردادهای مشترک است. API توسعه روی ۴۰۰۰، شهروند روی ۵۱۷۳ و پنل روی ۵۱۷۴ اجرا می‌شوند.

`packages/contracts` ورودی‌های Zod، مدل فرم، enum، ماشین حالت و کد رهگیری؛ `packages/i18n` نرمال‌سازی فارسی، اعداد و تاریخ؛ `packages/ui` اجزای پایه و توکن‌ها را نگه می‌دارند. صفحات و primitiveهای فعلی در `apps/citizen-web/src` هستند. پنل مستقل همان صفحات رسیدگی را reuse می‌کند. جداسازی bundle پنل از شهروند بهینه‌سازی مرحله بعد است.

## ذخیره و گردش‌کار

مدل اصلی شامل شهر، سازمان، واحد، عضویت، سرویس، فرم نسخه‌دار، کاربر، نشست، OTP، درخواست، تاریخچه، ارجاع، پیام، پیوست، اعلان، audit و idempotency است. schema و migration SQL در API وجود دارند. PGlite توسعه روی دیسک پایدار است؛ `DATABASE_URL` مسیر PostgreSQL مستقل را فعال می‌کند. نتیجه تست فعلی فقط برای PGlite است.

ثبت درخواست، تاریخچه اولیه، اعلان و audit در یک تراکنش انجام می‌شود. کلید idempotency در همان تراکنش رزرو و به درخواست متصل می‌شود؛ ارسال هم‌زمان با یک کلید درخواست دوم نمی‌سازد. فرم با schema خدمت در سمت سرور اعتبارسنجی می‌شود و کلیدهای ناشناخته حذف می‌شوند. پیوست باید متعلق به شهروند و هنوز متصل‌نشده باشد.

تغییر وضعیت توسط ماشین حالت کنترل و همراه تاریخچه، اعلان و audit ذخیره می‌شود. انتقال سازمان، مسئول قبلی را پاک می‌کند؛ سازمان جدید و دلیل در تاریخچه و اعلان دیده می‌شود. امتیاز بازخورد را ثبت می‌کند؛ بسته‌شدن همچنان عمل کارشناس است. بازگشایی فعلی برای نتیجه حل‌شده وجود دارد.

## مرز دسترسی

دو کوکی HttpOnly با نشست opaque و hash ذخیره‌شده، یکی شهروند و دیگری کارشناس. نشست‌ها قابل چرخش و ابطال‌اند. مالکیت در خواندن/پیام/امتیاز/بازگشایی بررسی می‌شود. کارتابل و عملیات رسیدگی به عضویت فعال سازمان محدودند؛ دسترسی سازمان دیگر `403` است. مدیر پلتفرم دسترسی سراسری دارد؛ کنترل دلیل دسترسی و مجوزهای ریزدانه مدیر و واحد کار باقیمانده است.

OTP با HMAC، انقضا، تعداد تلاش و فاصله ارسال محدود است؛ فقط کد آزمایشی نمایش داده می‌شود. تولید بدون SMS با خطای مشخص متوقف می‌شود. CORS برابری دقیق origin را می‌سنجد؛ Origin نامعتبر برای درخواست تغییردهنده رد می‌شود. Helmet فعال است؛ CSP اختصاصی static و HTTPS باید در reverse proxy اعمال شوند. API header پراکسی ناشناس را مبنای هویت IP قرار نمی‌دهد؛ محدودیت سراسری پشت پراکسی باید متناسب با زیرساخت تنظیم شود.

پیگیری عمومی فقط کد، وضعیت و زمان تغییر دارد؛ متن، نام، مختصات و شناسه داخلی منتشر نمی‌شود. پیشنهاد مشابه فقط از داده دارای publicVisibility استفاده می‌کند؛ فرایند انتشار عمومی این نسخه فعال نیست. دانلود فایل با URL امضاشده ۱۰ دقیقه‌ای انجام می‌شود.

## API و رابط

`/openapi.json` و `/docs` سند OpenAPI 3.1 را از routeها می‌سازند. `/health` سلامت فرایند را نشان می‌دهد، نه آمادگی تمام وابستگی‌ها. خطاها کد، متن فارسی و correlation ID دارند. فهرست درخواست‌ها محدود به `limit` است؛ cursor helper موجود است ولی هنوز به همه مسیرها و UI متصل نشده است.

پرونده، کارتابل و اعلان با refresh و polling به‌روزرسانی می‌شوند. داده خصوصی کش عمومی ندارد. PWA فقط دارایی‌های پوسته را ذخیره می‌کند؛ sessionStorage پیش‌نویس متن را در نشست مرورگر نگه می‌دارد. ارسال مجدد دستی و با همان idempotency key است.

## دستیار

نسخه فعلی provider واژه‌محور است و از کاتالوگ پیشنهاد می‌سازد. هیچ اتصال مدل زبانی یا RAG، حتی با کلید محیطی، ادعا نمی‌شود. ثبت به آن وابسته نیست و انتخاب دستی همیشه ممکن است. موارد محتمل خطر فوری از مسیر معمول تفکیک می‌شوند؛ شماره تماس بدون منبع معتبر درج نشده است.

## مراحل بعد

adapterهای سازمانی، SMS، AI، پرداخت و GIS از هسته درخواست جدا بمانند. فعال‌سازی وابسته به قرارداد، کلید و تست معتبر باشد. outbox/queue، ظرفیت تراکنشی نان، تأیید و انقضای محتوا، دسترسی چندشهر و سیاست retention پیش‌نیازهای فاز بعدند. پوشش کامل در `REQUIREMENTS_COVERAGE.md` ثبت شده است. ماژول‌های مالی و نانوایی هنوز مدل اجرایی و migration ندارند و پیاده‌شده تلقی نمی‌شوند.
